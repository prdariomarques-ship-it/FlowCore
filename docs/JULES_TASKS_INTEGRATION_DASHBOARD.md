## Context — what already exists (Sprint 17, Milestone 6)

`service.py` has an `integrations_status()` aggregator that live-probes three
integrations concurrently and returns a list of dicts:

```python
# service.py
async def integrations_status() -> list[dict]:
    checks = [("Outlook / Calendar", _check_outlook), ("WhatsApp", _check_whatsapp), ("Ollama", _check_ollama)]
    async def _run(name, fn) -> dict:
        start = time.monotonic()
        try:
            result = await fn()
        except Exception as e:
            result = {"status": "error", "detail": str(e)}
        latency_ms = round((time.monotonic() - start) * 1000, 1)
        return {"name": name, "latency_ms": latency_ms, "checked_at": <iso utc>, **result}
    return list(await asyncio.gather(*(_run(name, fn) for name, fn in checks)))
```

Each `_check_*` function returns `{"status": "ok"|"not_configured"|"not_authenticated"|"unreachable"|"error", "detail": str}`.
`GET /api/integrations/status` → `{"integrations": [...]}`. CLI: `flowcore.py integrations`.
MCP: `flowcore_integrations_status`. Web UI: "Integrações" tab in `web/index.html`
(10th nav item), one `.card` per integration with a colored `.tag` status badge.

**This pattern is the contract. Every task below extends it — nobody invents a
second way to represent integration status.**

**Standing decision, do not relitigate without asking the user:** this dashboard is
live-probe only, no persisted history. "Last successful communication" = the
`checked_at` field from the most recent probe, not a synchronization log. Nothing
today records historical check results anywhere, and building that would mean a new
table plus a background job — out of scope here, already decided with the user for
Milestone 6.

**Data contract addition needed for all tasks below:** add an explicit `error: str | None`
field to every check's return dict (currently errors are folded into `detail`).
`detail` = always-present informational text. `error` = populated only when
`status != "ok"`, `None` otherwise. Do this as a small first task (Task 0) since
every other task's UI work depends on it.

## Task 2 — Backend: Android capabilities summary check

**Files:** `service.py`

New `_check_android()`. Use the existing `_registry` (`CapabilityRegistry`, already a
module-level singleton in `service.py`) to check **availability only** — do not
invoke capabilities that have side effects (sending a notification, reading
clipboard) just to check status. `registry.get(capabilityName)` returns an adapter
or `None` — that's the presence check, it doesn't call anything:

```python
async def _check_android() -> dict:
    caps = ["getBattery", "getClipboard", "sendNotification", "listInstalledApps", "getNetworkInfo"]
    available = [c for c in caps if _registry.get(c) is not None]
    if not available:
        return {"status": "unreachable", "detail": "No Android capabilities available on this platform", "error": None}
    if len(available) < len(caps):
        return {"status": "ok", "detail": f"{len(available)}/{len(caps)} available: {', '.join(available)}", "error": None}
    return {"status": "ok", "detail": f"All {len(caps)} capabilities available", "error": None}
```

**Important:** on the actual dev machine (Debian/WSL2, see `FLOWCORE_CONSTITUTION.md`
→ this repo's environment model in `ARCHITECTURE.md`), this will correctly show
`"unreachable"` or a partial list — that's expected, not a bug, since Termux-only
capabilities have no WSL2 equivalent for several of these. Do not "fix" this by
faking availability.

**Verification:** pytest with `_registry.get` mocked to return/not-return adapters
for each combination. Live-check on this dev machine — confirm it reports the same
partial availability already seen in Milestone 1 (battery/wifi available via
`LinuxAdapter` fallback, clipboard/notify/apps unavailable).
